# 5.0

* **Release Date:** 2026-07-09

## Overview

This release adds OAuth 2.0 authentication for the Okta management API, moves the project to the maintainer's `BoldlyGrow` namespace, extends framework support to Laravel v13, and drops support for the legacy Laravel v8, v9, and v10 releases. The legacy SSWS API token remains fully supported, so existing single-token deployments continue to work without changes.

### New Features

- Add Laravel v13.x support
- Add OAuth 2.0 for Okta authentication using the Client Credentials grant with a `private_key_jwt` client assertion
- Add `ApiToken` class that mints, caches, and returns a short-lived scoped Bearer or DPoP-bound access token
- Add Demonstrating Proof of Possession (DPoP) support for OAuth 2.0 access tokens with the `OKTA_API_DPOP` variable and a `DpopProof` class
- Add private key resolution from an inline PEM string (`private_key`) or a PEM file path (`private_key_path`)
- Add a per-call `scope` argument to the request methods and `testConnection()`, required when using OAuth, for least-privilege scoping
- Add an `okta-api-client:jwk` Artisan command and a `PublicKeyJwk` action to generate an RSA key pair and convert a public key to a JWK for the Okta service app
- Add configurable `testConnection()` probe endpoint for service apps that are not granted the `okta.orgs.read` scope
- Add authentication-mode aware `401` error messaging
- Add the reason for a failed request to every exception message and to the audit log `errors` array, including the `errorCauses` returned for a validation failure and the `WWW-Authenticate` error returned for an OAuth 2.0 resource server failure
- Add a `ServiceUnavailableException` that is thrown for a `503` response
- Add a Pest test suite with Orchestra Testbench (`composer test`)

### What's Changed

- **Package Architecture**
    - The Composer package and namespace has been renamed from `provisionesta/okta-api-client` to `boldlygrow/okta-api-client`.
        - **Why:** The project is consolidating under the maintainer's `BoldlyGrow` organization alongside the related audit and actions packages.
    - The PHP namespace changed from `Provisionesta\Okta` to `BoldlyGrow\Okta`.
    - The audit logging dependency changed from `provisionesta/audit` to `boldlygrow/audit-log`. The imported class changed from `Provisionesta\Audit\Log` to `BoldlyGrow\AuditLog\AuditLog`.
    - The `provisionesta/okta-api-client`, `gitlab-it/okta-sdk`, and `glamstack/okta-sdk` package names are retained as `replace` aliases for a smoother upgrade.
    - Added `illuminate/console` and an explicit `ext-openssl` requirement to `composer.json` for the new Artisan command and JWT signing.
    - Removed support for the legacy Laravel v8, v9, and v10 releases. The minimum PHP version is now `^8.2` and the supported Laravel range is `^11.0`, `^12.0`, and `^13.0`.
        - **Why:** These versions are past their maintenance windows, and the `boldlygrow/audit-log` dependency already requires Laravel v11+ and PHP v8.2+, so the legacy ranges could not resolve in practice.
    - Added a Pest test suite under `tests/Feature` that runs with `composer test`, using the same layout as `boldlygrow/audit-log`. All Okta endpoints are faked with `Http::fake()` and stray requests are prevented, so the suite never reaches the network.
        - Added `pestphp/pest` and `pestphp/pest-plugin-laravel` as development dependencies. Running the suite requires PHP v8.3 or newer; the package itself still supports PHP v8.2.
- **Error Handling**
    - Exception messages now include the reason that the Okta API returned for the failure, and use the format `METHOD CODE URL (Reason) <errorCode> <errorSummary> (Causes) <errorCauses>`.
        - **Why:** Only `errorCode` and `errorSummary` were read from the response body. For a validation failure the `errorSummary` only names the object that failed (ex. `Api validation failed: profile`) and the actionable per-attribute reason is returned in `errorCauses`, which was silently discarded.
    - `errorCauses` entries are now flattened onto the message (ex. `(Causes) firstName: The field cannot be left blank, email: Does not match required pattern`).
    - The `error` and `error_description` keys returned by the OAuth 2.0 token endpoints are now read as well.
        - **Why:** These responses contain neither `errorCode` nor `errorSummary`, so an OAuth failure produced a message with the method, status code, and URL followed by two trailing spaces.
    - If the response body uses none of these keys, the body is appended (truncated to 1000 characters) instead of being discarded.
    - If the response body is empty, the `error` and `error_description` from the `WWW-Authenticate` response header are used as the reason (ex. `(Reason) invalid_dpop_proof 'htu' claim in the DPoP proof JWT is invalid.`).
        - **Why:** Okta returns OAuth 2.0 resource server failures, such as a rejected DPoP proof, as a `400` or `401` with an empty body and the reason only in this header.
    - A `503` response now throws the new `ServiceUnavailableException`.
        - **Why:** `503` was mapped in the log types as `critical.server-unavailable`, but the exception switch had no case for it, so no exception was thrown and the caller silently received a failed response object.
    - `ServerErrorException` is now thrown with the same message format. It was previously thrown with a `json_encode()` of the response body, which dropped the method and URL and produced the string `null` for a non-JSON body.
    - The audit log `errors.error_message` value now contains the same parsed reason. `errors.error_code` is unchanged.
    - A decoded copy of the URL is appended to the message when it differs from the URL that was requested (ex. a `filter` query string). The encoded URL is still shown first and is the one that reproduces the request.
    - **No action is required** unless you parse exception message strings. The existing exception classes, status code mapping, and `OKTA_API_EXCEPTIONS` behavior are unchanged.
- **Authentication**
    - Added OAuth 2.0 for Okta as an alternative to the SSWS API token.
        - **Why:** Static SSWS tokens are long-lived org-wide credentials tied to an individual and expire after inactivity. An OAuth service app scopes access to exactly what is needed (for example read-only users, groups, and apps), rotates without human involvement, and pairs with a private key rather than a shared secret.
        - **How:** Configure an Okta API Services app with `Public key/Private key` client authentication, register the public JWK, and grant the required Okta API scopes. Set `OKTA_API_CLIENT_ID` and the key location variables. When `client_id` is present, the client sends an OAuth access token; otherwise it falls back to `SSWS`.
        - **Note:** Client ID and client secret is intentionally not supported. Okta only accepts `private_key_jwt` for tokens carrying management API scopes, and rejects a client secret with `invalid_client: Client Credentials requests to the Org Authorization Server must use the private_key_jwt token_endpoint_auth_method.` A client secret only works against a custom authorization server for custom scopes, which cannot read Okta resources.
    - The `key_id` (`OKTA_API_KEY_ID`) is required for OAuth connections and is always sent as the `kid` header of the client assertion. A missing `key_id` throws a `ConfigurationException` before a token is requested.
        - **Why:** Okta rejects a client assertion without a `kid`, so an unset key ID previously failed at the token endpoint with a less specific error.
    - The access token is requested once per unique connection, scope set, and DPoP setting, encrypted with the application's `APP_KEY`, and cached for 59 minutes by default. Okta fixes the access token lifetime at one hour.
        - The cache lifetime can be set with the `token_cache_minutes` config key or the `OKTA_API_TOKEN_CACHE_MINUTES` variable, as a whole number from 1 to 59. Any other value throws a `ConfigurationException`.
        - If Okta rejects the access token with a `401` response, it is removed from the cache with `ApiToken::forget()` so that the next request mints a new one. A `use_dpop_nonce` challenge does not remove it.
        - **Why:** A token that was revoked, or minted before the service app's granted scopes changed, would otherwise be rejected for the rest of the cache lifetime.
    - Added Demonstrating Proof of Possession (DPoP) support ([RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449)) with the `OKTA_API_DPOP` variable or the `dpop` connection array key. It is disabled by default.
        - **Why:** When the Okta service app has **Require Demonstrating Proof of Possession (DPoP) header in token requests** enabled, a token request without a DPoP proof is rejected with `invalid_dpop_proof`. A DPoP-bound access token cannot be replayed if it leaks, because every request must also carry a single-use proof signed by a key that only the client holds.
        - **How:** An ephemeral RSA key pair, separate from the `private_key_jwt` signing key, is generated each time an access token is minted and cached (encrypted) with the token. The token request carries a DPoP proof and is retried with the server-provided nonce after Okta's `use_dpop_nonce` challenge, signing a new client assertion for the retry. Each API request is sent with the `DPoP` authorization scheme and a new proof bound to the HTTP method, URL (without the query string, and percent-decoded since Okta compares it to the decoded request URL), and access token. A `use_dpop_nonce` challenge from the API is retried once with the nonce.
        - If DPoP is required by the service app but not enabled in the client, the `UnauthorizedException` message explains how to enable it.
        - The authorization scheme follows the `token_type` that Okta returns, so a `Bearer` token is still sent as `Bearer` if Okta does not bind the token.
    - All granted scopes can be requested in a single token, so one token is reused across users, groups, and apps requests. Scopes may also be requested per call.
- **Scopes**
    - Added a `scope` argument to `get`, `post`, `patch`, `put`, and `delete` for per-call scoping, mirroring the Google API client. It is appended as an optional trailing parameter, so existing SSWS calls are unaffected.
    - The scope is required when authenticating with OAuth. There is no config or environment default; omitting it throws a `ScopeException`. The `OKTA_API_SCOPES` variable and the `scopes` config key have been removed.
        - **Why:** The scopes granted to the Okta service app are the hard least-privilege ceiling. Requiring the scope at the call site keeps the requested authority next to the operation that needs it and avoids a broad default that silently widens every token.
    - The SSWS token path ignores the `scope` argument.
    - Each unique scope set is cached separately for the full token lifetime, so per-call scoping mints a few more tokens per hour without shortening caching.
- **Private Key Resolution**
    - The signing key is provided as an inline PEM string (`private_key`) or a PEM file path (`private_key_path`, with a leading `~` expanded). `private_key` takes precedence.
        - **Why:** Keeping the package to two simple key sources avoids conflating a logical secret name with a file path, and keeps the package free of any secrets-manager or cloud SDK coupling.
    - This package intentionally does not integrate with any secrets manager. Fetching the key from a vault or secrets manager is the consuming application's responsibility; the resolved PEM is passed in via the connection array or the published config. See the README for both patterns.
    - The key is resolved only on a token cache miss. The token cache key includes the `kid` and either the file path or a fingerprint of the inline key, so rotating the key takes effect without stale caching.
- **Connections and Configuration**
    - `validateConnection()` now accepts either a `token` (SSWS) or a `client_id` (OAuth). Validated keys are merged over the source connection array so OAuth keys provided at runtime are preserved through to `ApiToken`.
        - Both keys are nullable, so the unused credential from the published config (which resolves an unset `OKTA_API_TOKEN` or `OKTA_API_CLIENT_ID` to `null`) does not fail the format rules of the other authentication mode.
    - Added configuration keys: `client_id`, `key_id`, `private_key`, `private_key_path`, `dpop`, `token_cache_minutes`, and `test_uri`. Scope is passed per request, not configured.
- **API Requests**
    - `testConnection()` still probes `org` by default but now honors `OKTA_API_TEST_URI`, and accepts a `scope` argument for OAuth connections (ex. `ApiClient::testConnection(scope: 'okta.orgs.read')`).
        - **Why:** The `org` endpoint requires the `okta.orgs.read` scope. A service app granted only users, groups, and apps read would otherwise fail the connection test despite having valid credentials.
- **Error Handling**
    - The `401` exception message is now tailored to the authentication mode of the connection that was used for the request. Under OAuth it points to token expiry, scope grants, and JWK registration. Under SSWS it points to token rotation in `OKTA_API_TOKEN` or the connection array `token`.
        - **Why:** The mode is taken from the connection, not the config, so a request with an SSWS connection array is not reported as an OAuth failure when the config has a `client_id` (and vice versa).
    - A successful token endpoint response that is not JSON (ex. an HTML page from a proxy) throws an `UnauthorizedException` with the reason instead of a `TypeError`.

### Upgrade Steps

- Update `composer.json` to require `boldlygrow/okta-api-client:^5.0` and run `composer update`.
- Ensure your application is running Laravel v11, v12, or v13 and PHP v8.2 or newer before upgrading. Applications on Laravel v8, v9, or v10 must upgrade the framework first, or stay on `provisionesta/okta-api-client:^4.0`.
- Perform a find and replace across your code base from `Provisionesta\Okta` to `BoldlyGrow\Okta`.
- If you reference the audit logger directly, update `Provisionesta\Audit` to `BoldlyGrow\AuditLog`.
- Re-publish or update the config file so the new OAuth keys are present: `php artisan vendor:publish --tag=okta-api-client`.
- Existing SSWS deployments require no functional change. Keep `OKTA_API_URL` and `OKTA_API_TOKEN` as-is.
- To move a connection to OAuth:
    - Create an Okta API Services app with `Public key/Private key` client authentication and register your public JWK.
    - Grant the app the Okta API scopes it needs (for example `okta.users.read`, `okta.groups.read`, `okta.apps.read`) and assign a least-privilege admin role.
    - Set `OKTA_API_CLIENT_ID` and `OKTA_API_KEY_ID` (required). Scopes are passed per call via the `scope` argument, not an environment variable.
    - Provide the private key with `OKTA_API_PRIVATE_KEY_PATH` (a PEM file) or `OKTA_API_PRIVATE_KEY` (an inline PEM), or pass `private_key` in the connection array. For production, resolve the key from your secrets manager in your own code and pass it in the connection array.
    - If the service app is not granted `okta.orgs.read`, set `OKTA_API_TEST_URI` to an endpoint it can reach.
    - If the service app has **Require Demonstrating Proof of Possession (DPoP) header in token requests** enabled, set `OKTA_API_DPOP=true` (or `'dpop' => true` in the connection array). No additional keys are needed.
- This is not an exhaustive list. Review the `README.md` for the latest syntax and usage guidelines.
